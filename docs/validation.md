# 实践验证与压测计划

状态：验收计划与分阶段证据索引。S2 核心与持久化证据见 [S2 实施结果](validation/s2-results.md)，S3 后台和真实 Agent 验收状态见 [S3 验收记录](validation/s3-agent-acceptance.md)。完整 U/R 矩阵、真人交互及 L 压力场景尚未完成；S1 结构检查继续独立保留。

本项目要验证三个不同的问题：协议是否足以表达[产品链路](product.md)，Go 实现是否忠实且可靠地执行这些规则，以及给定机器与负载下能支撑怎样的日常使用规模。三类结论分别记录，不以一个“压测通过”替代。

## 开始运行验证前的条件

- 固定[上游协议版本](../protocol/README.md)、demo commit 与协议文件摘要；以固定版本的 Schema 和语义共同判定。
- 定义公开传输绑定、身份映射、注册与定向策略、查询与事件接续接口，以及持久化和失败响应保证。没有这些约定时，相关场景记为未就绪。
- 固定 [skill 与实施登记契约](agent-integration.md)、ActivitySession 关联和 presence 规则，以及 WakeRequest/LaunchProfile 的授权、版本、对账与重试边界；配置样例参见[集成目录](../integrations/README.md)。
- 用一个真实 Go authority、一个人、至少两个独立 Agent 客户端完成请求；客户端通过公开接口观察，不读取数据库来绕过用户流程。
- 两个独立客户端按公开规格分别实现消息收发，不导入服务的领域实现作为结果判定器。另一套独立 authority 的互操作属于更后续证据，不由两个客户端自动证明。
- 使用可公开的合成任务与小型真实产物，例如一份说明文档及其评审意见；记录人工决定与产物引用，不把脚本自报结果当作实际交付内容验证。

先完成单条真实闭环，再扩展故障与负载。压测不得为提高成功率绕过身份、角色、revision、提交或验收步骤。

## 日常使用验收矩阵

以下完整日常使用场景尚未全部执行；S2/S3 对部分规则已有分层证据，不能据此将对应 U 场景整体标为通过。同一轮结果须记录对应编号、入口层次、证据位置和判定。

| 编号 | 实际场景 | 可观察的通过条件 |
|---|---|---|
| U01 | 人登记项目和任务，Agent A 领取、报告并交付，人验收 | 公开任务事实经历 offered→claimed→active→submitted→completed；正式提交后不会自行完成 |
| U02 | Agent A 发起任务，Agent B 交付，A 验收 | issuer 来自可信身份；人的管理员入口和 B 都不能替 A 作决定 |
| U03 | A 发起关联评审任务，人提交意见 | 人能正常承接与交付；评审完成不改变父任务状态或决定权；意见与验收决定分别可读 |
| U04 | 登记两个同名 Agent，更新显示名或接入凭据 | 身份保持稳定且彼此独立；历史作者不变，名称相同不能冒充对方 |
| U05 | 创建指定给 A 的任务，B 尝试领取；随后显式转交 | 任务第一次可见时限制已生效；B 不能 claim；有当前承接时不能直接改指定对象夺取执行权 |
| U06 | 一个目标拆成多个任务，由 A、B 分工 | 多任务可以并行；每个 Task 只有一个当前承接；子任务成功或失败不自动改变父任务 |
| U07 | 汇总任务引用多份交付，写入项目交接记录，后续客户端接续 | 汇总和 handoff 标明来源、版本与未决项；新客户端能通过公开查询找到上下文，未验收内容不会被标成完成 |
| U08 | 执行中修订预期，交付后再修订，发起方接受旧依据结果 | 旧 Run/Submission 的依据不变；Decision 同时保留工作依据与评价时版本；不能把旧执行偷偷改成新依据 |
| U09 | 拒绝交付后重开，或执行失败后重开 | 历史事实保留，新承接采用新代次；执行失败与验收拒绝有不同记录，旧交付不能再次成为当前决定目标 |
| U10 | 已接受任务的参与者再次登录并读取时间线 | 当前快照、历史交付和决定可对应；客户端不靠本地私有会话才知道任务完成情况 |
| U11 | Agent 配置 skill 的服务地址、稳定身份、凭据引用，登记或更新资料 | 接入经宿主验证和管理者政策批准；显示资料不会改身份或授予权限，凭据不出现在任务与公开记录中 |
| U12 | skill 接受已有任务并建立 ActivitySession | 没有重复创建任务；会话与成功取得的 Task/Assignment/Run 对应；provider/host/workspace 是来源资料，执行会话的可信关联另由宿主验证 |
| U13 | Agent 自发工作，skill 组合 create、claim、start 与实施登记 | 真正 Agent 是 issuer，步骤及中间结果可查；结束登记后任务不会自动完成，交付与明确验收各自留痕 |
| U14 | 会话 heartbeat、阶段汇报、结束后换客户端接续 | presence 与任务状态分离；接续者核对权威事实后恢复记录，不能靠会话 ID 恢复旧执行权 |
| U15 | A 先创建定向任务，再申请按已批准配置唤起 B | 可查已提交任务、WakeRequest 与使用的配置版本；启动结果与 B 的 claim 分开，未配置唤起也能主动领取 |

每轮试用另记录接入步骤、额外手工操作、需要猜测的字段、找回上下文所需步骤和未表达的业务意图。产品“可用”的证据包括这些实际使用问题得到处理，不只包括返回成功状态码。

## 协议一致性与故障矩阵

| 编号 | 注入条件 | 必须保持的事实 |
|---|---|---|
| R01 | 多个客户端对同一 offered Task 真正并发 claim | 最多一个成功承接；其余失败不产生多余 Assignment 或成功事件；这必须由并发运行验证，串行调用不能代替 |
| R02 | 相同命令并发重试、提交后丢失响应、完成后重放 | 一次成功事实只提交一次；重放返回原回执而不推进当前任务；回执读取权与新执行权分别检查 |
| R03 | 同幂等键改内容，或向其他任务复用同键 | 按协议拒绝冲突；精确数字、布尔与数字、缺失与 null、对象键序等比较符合协议，不由浮点舍入或 Go 零值改变含义 |
| R04 | 失序命令、旧 revision、释放后旧执行者迟到提交 | 明确拒绝；当前承接、Run、Submission、事件和 revision 不被污染；客户端重读事实后再决定下一步 |
| R05 | 在持久提交前、提交后响应前强制终止进程并重启 | 每个请求要么没有成功提交，要么完整保留任务、事实、事件与回执；响应未知时用原命令重试，不盲目创建新操作 |
| R06 | 停用当前承接 Agent 或 issuer，再恢复同一身份 | 无自动完成或释放；新命令受准入限制；历史读取按独立政策判断；issuer 停用不授权管理员代验收 |
| R07 | 定向策略更新与 claim 竞争，或创建时中断策略写入 | 策略与承接检查使用一致视图；没有“先公开可抢、后定向”的窗口；失败不留下缺失策略的可领取任务 |
| R08 | 消费者断连、重复事件、乱序到达或游标缺口 | 去重后恢复同一任务事实；发现 revision 缺口并按公开读取契约修复；不会用旧事件覆盖新版本 |
| R09 | 取消活跃或已提交任务，或终态收到新命令 | 保留真实执行和交付历史；取消不宣称外部工作已经停止；终态不被普通新命令复活 |
| R10 | 存储写失败、容量不足或服务过载 | 不确认未持久提交的成功；不出现部分事实；返回可区分的失败并可核对结果，不靠删除幂等历史恢复写入 |
| R11 | skill 的 create 成功但 claim 未执行，或 start/登记响应未知后重试 | 保留每步原命令身份并核对回执；不重复创建 Task、Assignment、Run 或会话，不把部分完成显示为全部成功 |
| R12 | ActivitySession 心跳丢失、重复、失序或客户端崩溃 | presence 可变为失联但不释放承接、失败 Run 或完成 Task；旧心跳不能覆盖较新会话事实或获得执行权 |
| R13 | 唤起失败、重复投递或外部启动后响应丢失 | 任务继续存在；WakeRequest 留下独立结果；未知结果不盲目再次启动，受控重试可追踪；启动不产生伪造 claim |
| R14 | 任务创建回滚或尚未提交时触发唤起；分别在authorize前后取消或改指定对象 | 未提交任务没有外部启动；authorize前失效记skipped；authorize后仍可能启动，目标必须重新校验claim/start；唤起回执不改业务任务事实 |
| R15 | 排队后停用目标身份、撤销配置授权或更新 LaunchProfile | reserve/authorize事务内重新检查；授权后的撤销不承诺原子停止外部spawn；历史请求保留原配置版本，catalog_revision和配置事件接续一致；历史读取与新启动资格分开 |
| R16 | 任务内容或参数包含 shell 元字符、路径跳转、伪造凭据引用或未授权启动配置 | 输入作为受约束数据处理，不能注入命令、越过目录/凭据范围或执行任意脚本；拒绝结果可审计且无外部启动 |
| R17 | 同一 ActorRef 被重复唤起成两个进程，跨 session 复用承接，或承接响应未知后恢复 | 宿主可信核对 ActivitySession 的执行归属；不能仅凭相同 Agent 身份使用另一会话的 Assignment/Run；未知结果先查原回执与归属，不额外启动或越权接管 |

故障注入可在测试环境通过受控进程终止、响应丢弃和存储失败点实现；验收结果通过公开接口核对。内部追踪用于解释根因，不能替代公开结果。具体注入工具在服务与存储选定后再定。

唤起验证先使用测试宿主批准的无害记录程序，核对真实启动次数、配置版本与传入的数据，再接入受控 Agent 进程；模拟成功回执不能证明外部副作用可靠。不得为这组测试执行任务正文提供的命令，也不得使用生产凭据。当前唤起场景仍处于设计阶段，不配置或调用启动程序。

一致性断言必须同时检查 Task、承接、执行、交付、决定、事件和回执，不只检查最终状态字符串。覆盖 11 个核心操作的正常路径、状态守卫、身份与对象归属守卫后，才能声明实现了整个草案支持范围。

## 压测工作负载

负载工具暂不选定，当前不提供 benchmark 程序。先以固定合成数据与真实 binding 建立小规模基线，再按任务量、活跃参与者数、产物引用大小和历史长度逐级增加负载。每级先核对一致性，再评价速度。

| 编号 | 工作负载 | 重点观察 |
|---|---|---|
| L01 | 多个独立任务执行完整创建至验收链路 | 跨任务吞吐、端到端完成延迟、写入队列与存储竞争 |
| L02 | 大量参与者争抢同一个任务 | 成功承接始终唯一；冲突率和冲突响应延迟单列，不把冲突算成成功吞吐 |
| L03 | 长时间执行任务持续报告，并混入预期修订和提交 | 报告放大、同任务 revision 冲突、历史增长和提交是否被报告流阻塞 |
| L04 | 大比例重复请求、响应未知重试与错误请求 | 回执成本、唯一提交数与重放数、拒绝路径的资源消耗；重试不扩大事实数量 |
| L05 | 多读取方与慢消费者，配合历史查询和事件补读 | 消费积压、读取尾延迟、分页稳定性、任务写入受读取影响的程度 |
| L06 | 长时间稳态负载及历史持续增长 | CPU、内存、文件句柄、数据库与 WAL 增长、每次操作读写量及延迟漂移 |
| L07 | 负载中重启并恢复服务，消费者追赶积压 | 服务恢复时间、回执可恢复性、快照与事件一致性、追赶速度及恢复期错误率 |
| L08 | 超过已测容量后停止加压并降载 | 过载响应是否明确、资源是否有界、是否能恢复到基线；已确认持久提交的事实不丢失，无死锁或假成功 |
| L09 | 大量 ActivitySession heartbeat、阶段更新与核心任务写入混合 | presence 写放大、会话存储增长与尾延迟；登记流量不能使领取、交付和验收饥饿，心跳不制造核心事件 |
| L10 | 批量定向任务与 WakeRequest，慢启动宿主、同身份重复进程、未知结果及恢复 | 唤起队列积压、受控并发、重试放大、实际启动次数和会话归属对账时间；唤起服务受阻不阻止其他任务主动领取 |

每次报告必须包含机器 CPU/内存/磁盘、Go 与数据库版本、demo 与协议版本、持久化配置、数据规模、客户端实现、并发数或到达率、请求比例、预热时长、测量时长和重复次数。记录客户端实际发送与完成量，避免只测服务内部函数或省略排队时间。

压力流量使用合成参与者与明确标注的自动决定，不宣称发生了真实人的 review。真实使用中的人工判断时长与服务处理延迟分开记录；U03 的人工协作证据不能用压力脚本代替。

至少报告按操作分类的 p50/p95/p99 延迟、端到端链路耗时、唯一成功提交吞吐、重放量、预期冲突/拒绝量、意外错误率、客户端与服务端积压、CPU/内存、数据库/WAL 增长和恢复时间。核心命令、ActivitySession 写入与唤起请求分别统计；外部实际启动次数及成功 claim 数也分别记录。分母与采样窗口须清楚，超时和失败不能从延迟统计中静默删除。

当前不承诺 QPS 或响应时间目标。先获得可复现基线，再结合每日使用要求设定容量范围、延迟目标与资源预算，并在报告中明确通过条件。压测得出的容量只适用于该实现、硬件、配置与工作负载，不能宣称为协议所有实现的性能保证。

## 判定与上游反馈

| 归类 | 判定依据 | 处理去向 |
|---|---|---|
| 协议歧义或缺口 | 真实场景没有明确表达，或符合现有文字的实现可能得出互相矛盾的事实 | 整理最小场景回馈协议仓库；先澄清规范与版本，再更新 demo 的固定来源 |
| demo 实现缺陷 | 上游规则明确，但 Go 服务、适配或客户端违反它 | 在本项目修复并增加对应回归证据；不以修改协议掩盖错误 |
| 应用策略缺口 | 注册、定向、汇总、身份恢复等业务规则尚未定义 | 补齐应用契约及验证，不默认把所有产品要求移入任务核心 |
| 容量或性能瓶颈 | 语义保持正确，但特定负载下延迟、资源或恢复不满足已定目标 | 定位实现和配置，重测相同负载；若涉及协议表达成本，再附证据讨论上游 |

每个问题报告包含：场景编号、上游 commit/摘要、demo commit、环境、已匿名化的最小命令及身份角色、期望与实际、复现步骤、相关公开结果/事件、是否稳定复现及影响范围。不能附真实凭据、私人提示词、数据库或完整业务会话。

设计过程中暴露的语义缺口先进入[协议设计发现](protocol-findings.md)，标注推导依据、开放问题和待验证场景。没有运行复现时，不能填写已观察到的故障或把宿主规则当成上游既有保证。R17的会话归属已在S1固定proof/transfer，但仍需工程验证，且不隔离复制了全部凭据的同主体进程。

S1另提供[18项黑盒行为规格](../contract/v1/vectors.json)及结构正反例。静态工具只检查这些请求的形状与错误映射，行为预期没有执行；它们是U/R/L场景的实施输入，不替代其真实验收。

上游问题修订后，更新本项目的协议锁定信息，重跑相关功能、故障与容量场景，保留前后差异。不直接改本地协议副本，也不把仅通过 Schema 的消息宣称为行为兼容。采用同一个离线参考模型互测只能提供模型层证据；真实独立实现互操作需单独记录双方实现与公共传输结果。
