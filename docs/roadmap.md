# 从骨架到协议实践证据

日期：2026-10-31。当前阶段：S0 骨架。后续阶段均未实现或执行，不以文档和 CI 编译通过替代验收。

| 阶段 | 交付与任务 | 退出条件 | 当前状态 |
|---|---|---|---|
| S0 独立骨架 | 产品目标、Go 模块边界、固定协议来源、开源文件、验证矩阵和压测计划 | 来源和链接可核对，Go 包可编译，独立设计复核；无假成功 API | 已建立，静态检查与独立审查通过 |
| S1 接入契约 | 固定本项目 HTTP binding、注册/停用、凭据映射、目标资格与创建幂等、查询/cursor | 完整消息/错误/权限/事务表和黑盒向量；明确未解决事项 | 未开始 |
| S2 Go 核心与持久化 | 11 操作、精确 JSON、SQLite 事务与回执事件、独立语义反例 | 结构与行为检查通过；竞争、重试、崩溃恢复和原子性有证据 | 未开始 |
| S3 最小日常闭环 | 项目、身份目录、指定 Agent、公开接口、skill 接入与实施登记、人登记和验收 | 一个人、两个独立客户端/Agent 完成基础 U 场景；已有任务/自发实施、会话恢复均通过公开接口 | 未开始 |
| S4 委派与连续使用 | 多任务分工、受控可选唤起、时间线、汇总/接续、重开返工；据使用反馈确定前端 | 唤起失败/重复/同身份多进程受控；真实日常接续不丢上下文、不篡改历史 | 未开始 |
| S5 故障与负载 | R/L 系列场景、基线、逐级负载、饱和与恢复 | 语义不变量始终成立；指定环境的可用容量、延迟和恢复范围可复现 | 未开始 |
| S6 首个可用 demo 版本 | 使用入口、部署说明、升级/备份、已知限制与发布证据 | 用户闭环、可靠性、容量及安全边界符合实际证据；明确支持的协议提交与 binding | 未开始 |

故障验证应从 S2 起随实现加入，压力基线从有运行服务后建立，不是等功能全部完成才发现并发问题。S3 的“独立客户端”指独立编写协议调用，而不是两个客户端名复用同一内部测试函数。S6 才对应可用版本发布；公开 S0 源码不代表服务已可用。

## 下一实施切片

先完成 S1：

1. 固定 ActorRef 注册、凭据映射和停用/恢复策略；明确读取历史的范围。
2. 固定命令包装、创建时项目与目标策略的原子事务，以及完整请求幂等。
3. 固定真实查询、快照水位与 cursor 接续，不复用 M1 私有数据结构。
4. 为成功、拒绝、未知结果和重复请求写公开输入/输出向量，之后再选 Go JSON Schema 工具和 SQLite 驱动。
5. 固定 skill 配置与身份登记、ActivitySession 组合操作、执行会话绑定、LaunchProfile 权限和 WakeRequest 的提交/核对边界。

本轮不提前实现业务，不启动服务，也不选前端框架。设计中的待定点见[绑定草案](binding.md)。

## 上游反馈闭环

设计阶段即可登记[协议实践发现](protocol-findings.md)，标注规格推导与待实测项。每个实践问题先按[验证计划](validation.md)归类，附[证据模板](evidence-template.md)。协议缺口形成可审查的上游提案，Go 实现和宿主问题在本仓库处理；本轮不自动发布 issue。任何上游修订都要经过[协议升级记录](../protocol/UPGRADES.md)和重新验证，不让 demo 私有补丁成为隐含协议。

压测先产出测量结果，再给适合本机配置和使用规模的容量目标。零双重承接、零重复提交事实、零部分提交等语义不变量始终是硬条件，不能用吞吐指标掩盖。外部进程启动和外部业务副作用不自动获得 exactly-once 保证。吞吐/延迟数字不推广为协议所有实现的承诺。
