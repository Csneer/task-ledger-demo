## 下一实施切片

下一阶段 S3：在已实现的 Go 核心与持久事务上接入[公开 binding](binding.md)，形成能够实际使用的最小闭环。

1. 实现 HTTP 入口与带外 Bearer 凭据映射，将可信身份和 read/write/admin 能力交给应用层；网络调用者不能自报 Host。
2. 接入公开项目/身份/任务查询、快照与签名 cursor，验证断连后按公开事实恢复。
3. 实现薄客户端与可安装 skill，完成已有任务、自发实施、登记/汇报/交付及人验收；组合步骤保留独立幂等身份。
4. 使用一个人和两个独立客户端完成基础 U 场景，并通过 HTTP 重跑相关并发、重试、权限和恢复反例。受控 launcher、handoff 与连续委派留在 S4。

S2 已实现的 10 个应用动作提供项目、目录、会话及定向规则所需的事务基础；它们仍是受信宿主 Go API。创建请求包含 wake 时明确拒绝且整体回滚，不把未实现的唤起当成成功。

S1明确保留的限制是全工作空间读取、带外凭据/启动配置、1000任务有界快照、无自动历史清理、无issuer移交及外部进程停止保证。它们是已选择的初版边界，不以TODO代替实施契约；如果日常使用需要扩展，新增版本与证据。

## 上游反馈闭环

设计阶段即可登记[协议实践发现](protocol-findings.md)，标注规格推导与待实测项。每个实践问题先按[验证计划](validation.md)归类，附[证据模板](evidence-template.md)。协议缺口形成可审查的上游提案，Go 实现和宿主问题在本仓库处理；本轮不自动发布 issue。任何上游修订都要经过[协议升级记录](../protocol/UPGRADES.md)和重新验证，不让 demo 私有补丁成为隐含协议。

压测先产出测量结果，再给适合本机配置和使用规模的容量目标。零双重承接、零重复提交事实、零部分提交等语义不变量始终是硬条件，不能用吞吐指标掩盖。外部进程启动和外部业务副作用不自动获得 exactly-once 保证。吞吐/延迟数字不推广为协议所有实现的承诺。
