# 从骨架到协议实践证据

日期：2026-10-31。当前阶段：S1 接入契约。后续运行阶段均未实现或执行，不以文档和 CI 编译通过替代验收。

| S1 接入契约 | HTTP binding、注册/停用、会话证明与接续、目标资格、创建幂等、查询/cursor、受控唤起 | 消息/错误/权限/事务表、机器规格与黑盒预期；静态校验和独立复核 | 已建立，静态校验与独立审查通过；行为未执行 |
| S2 Go 核心与持久化 | 11 操作、精确 JSON、SQLite 事务与回执事件、独立语义反例 | 结构与行为检查通过；竞争、重试、崩溃恢复和原子性有证据 | 未开始 |

故障验证应从 S2 起随实现加入，压力基线从有运行服务后建立，不是等功能全部完成才发现并发问题。S3 的“独立客户端”指独立编写协议调用，而不是两个客户端名复用同一内部测试函数。S6 才对应可用版本发布；公开 S0 源码不代表服务已可用。

## 下一实施切片

下一阶段 S2：按照已建立的 [binding 基线](binding.md)和[机器契约](../contract/v1/README.md)，先实现 Go 核心与持久事务，不先做前端或自动启动。

1. 精确 JSON 输入和 11 个核心操作；覆盖上游规则及独立反例，不把静态样例当状态机测试。
2. 选定 SQLite 驱动、迁移与隔离策略；建立事实/回执/事件及应用伴随数据的事务端口。
3. 实现当前执行绑定及注册/定向准入需要的存储边界，验证同键竞争、旧承接、部分提交与崩溃恢复。
4. 将本轮18个黑盒预期逐步转成真实测试。HTTP/skill/launcher分别在S3/S4接入；结构检查器继续独立保留。

S1明确保留的限制是全工作空间读取、带外凭据/启动配置、1000任务有界快照、无自动历史清理、无issuer移交及外部进程停止保证。它们是已选择的初版边界，不以TODO代替实施契约；如果日常使用需要扩展，新增版本与证据。

## 上游反馈闭环

设计阶段即可登记[协议实践发现](protocol-findings.md)，标注规格推导与待实测项。每个实践问题先按[验证计划](validation.md)归类，附[证据模板](evidence-template.md)。协议缺口形成可审查的上游提案，Go 实现和宿主问题在本仓库处理；本轮不自动发布 issue。任何上游修订都要经过[协议升级记录](../protocol/UPGRADES.md)和重新验证，不让 demo 私有补丁成为隐含协议。

压测先产出测量结果，再给适合本机配置和使用规模的容量目标。零双重承接、零重复提交事实、零部分提交等语义不变量始终是硬条件，不能用吞吐指标掩盖。外部进程启动和外部业务副作用不自动获得 exactly-once 保证。吞吐/延迟数字不推广为协议所有实现的承诺。
