# 产品范围与日常协作链路

状态：S1 契约与骨架，业务功能尚未实现。后端使用 Go，前端技术暂定。

Task Ledger Demo 是面向个人及小团队的人与 Agent 任务记录工具，也是检验任务协议是否足以支撑真实产品的独立 demo。它借鉴 p-drive 的项目上下文、执行记录和接续体验，以 [task-core-draft-1](../protocol/README.md) 表达任务事实，不依赖 p-drive 服务或数据格式。

## 希望解决的问题

用户能够知道一项工作由谁发起、目前谁在负责、预期怎样变化、交付了什么、谁确认了结果，以及下一位参与者应从哪里继续。一次 Agent 会话结束不再被当作任务完成；多人或多个 Agent 的并行工作应能各自留痕，再由明确的汇总动作连接起来。

首个可用版本先服务一个个人工作空间、一个权威服务及登记的参与者。Agent 通过配置 skill 接入服务，执行由自己的宿主承担；应用可按管理者预先批准的启动配置，异步唤起已登记 Agent 接任务。它不接受任务提供的任意脚本，也不负责模型选择。公开市场、支付、信誉、跨服务权威迁移和通用工作流引擎不属于首个闭环。

## 产品对象与协议对象

| 用户看到的内容 | 归属与含义 |
|---|---|
| 项目 | 应用层的目标、上下文与任务分组；引用完整 TaskRef，不另设一套任务状态 |
| 参与者目录 | 应用层登记人和 Agent；稳定 ActorRef 与显示名、能力描述、接入信息分离 |
| skill 接入配置 | 服务地址、稳定身份、凭据引用和登记资料；客户端适配配置，不是新的协议操作 |
| 任务卡片 | 协议 Task；创建必须有目标和预期结果，当前状态来自权威任务事实 |
| 本次承接与执行 | 协议 Assignment 与 Run；不是客户端会话或 Agent 进程的生命周期 |
| 实施会话记录 | 应用层 ActivitySession，记录 provider、host、workspace、session 以及 Task/Assignment/Run 关联；presence 不代表任务执行权 |
| 进展、交付与验收 | 分别对应 Report、Submission、Decision，界面不得合并为一个“完成”按钮 |
| 定向领取设置 | 应用层准入策略；限制哪些参与者能 claim，不代表已建立 Assignment |
| 可选唤起 | 应用层 WakeRequest 引用管理者配置的 LaunchProfile 及版本；启动结果与领取结果分别记录 |
| 项目摘要与交接记录 | 应用层的显式记录，保存作者、版本、来源任务及交付引用；不会改写任务状态 |
| 汇总工作 | 需要正式交付和验收时创建独立 Task；仅展示已有事实时生成可追溯的读取视图 |

应用层可以保留尚未发布的编辑草稿；只有提交 `task.create` 才产生协议中的 `offered` 任务。草稿不应被展示为一种新增协议状态。

## 首个日常使用闭环

1. **配置与登记。** 人建立自己的参与者身份，Agent 配置 skill 所需的服务地址、稳定身份及凭据引用，并提交或更新登记资料。工作空间管理者登记或批准接入；宿主验证身份，不能仅凭客户端名称取得资格。
2. **发布工作。** 人或 Agent 选择项目，填写目标与预期结果；可附输入资源和交付要求，并选择开放领取或指定已登记 Agent。
3. **承接与实施登记。** skill 先建立可信实施会话；符合准入策略的参与者发现并主动 claim 任务，宿主在成功领取时原子绑定会话与 Assignment，再 start 并记录 Run 关联。进展报告留下做法、阻塞、验证与下一步的公开摘要。
4. **分工与可选唤起。** 承接者需要其他参与者帮助时，创建明确关联的定向任务，可同时登记唤起请求，或在创建后另行申请。外部启动只在任务和请求均已提交后执行；目标仍需自行读取和领取任务。不同 Agent 同时处理不同任务，每个任务各自只有一个当前承接者。
5. **交付与验收。** 执行者提交结果后进入 `submitted`；该任务的发起者查看实际交付并接受或拒绝。拒绝保留理由与交付历史，需要重做时显式 reopen。
6. **汇总与接续。** 从项目摘要进入相关任务和历史交付；汇总者引用已有结果形成新的交付或交接记录。后续参与者明确引用前序任务和结果，不根据标题或时间邻近推断接续关系。

人的操作入口可以先由适配客户端承担，前端选型不改变这一闭环。是否易于每日使用，需要后续真实使用记录证明，不能从接口数量或页面数量推断。

## skill 接入与实施会话登记

skill 是面向 Agent 的接入说明与客户端适配入口，负责引导配置、身份登记、公开接口调用、实施记录和异常接续；服务仍是任务事实的权威。配置中的服务地址、ActorRef 和凭据引用各有用途，声明 ActorRef 不能绕过宿主认证。凭据本身存放在宿主提供的安全位置，不写入任务正文、报告或公开配置样例。登记可提交显示名、provider 和能力说明，不能借资料更新改成另一个主体或给自己授予权限。

实施登记借鉴 p-drive 的公开目标、路线、进展、决策、验证、阻塞与下一步记录，但使用独立的 ActivitySession，不引入 p-drive 运行依赖。provider、host、workspace 与客户端 session 是来源和定位资料，不是身份键或授权依据。ActivitySession 保存明确的 TaskRef 与已存在的 Assignment/Run 引用；没有成功承接或开始执行时，不伪造这些关联。

| 接入路径 | skill 的组合动作 | 必须保留的边界 |
|---|---|---|
| 接受已有任务 | 先建立可信 ActivitySession，读取任务与预期，claim 时原子绑定 Assignment，再 start 并补充 Run 关联 | 不重复创建任务；已有承接须同时核对宿主的会话执行归属，不能仅因 assignee 是同一 Agent 就复用他人的 Run |
| 自发开始工作 | 先登记会话与意图，填写目标和预期并 create；claim 时绑定会话，再 start 并关联 Run | 真实 Agent 是 issuer；不能因为“替人做事”就伪造人为发起者；自发任务仍需显式交付与 issuer 决定 |
| 恢复登记 | 查找原任务、承接、Run 与 ActivitySession，核对公开事实后更新会话记录 | 不因 session 恢复而复活旧承接；承接已结束时走新的合法任务操作 |

这些是多个可重试步骤，不承诺跨步骤自动原子完成。skill 必须保存各步的命令身份和已获回执；中途失败或响应未知时，先核对并重试原请求，不再创建同目标任务或无条件释放已经取得的承接。最终界面需要展示“任务已创建但未领取”等真实中间结果。

ActivitySession 的 heartbeat 只说明近期收到会话活动；丢失 heartbeat 不释放任务，不令 Run 失败，也不充当协议租约续期。结束实施登记只结束这条会话记录，不能直接把 Task 设为完成。正式结果经 `run.submit` 提交后等待 issuer 的明确决定；自发任务中的 Agent 也必须留下该决定，不能由登记 end 隐式代办。详细接入设计见 [Agent 集成](agent-integration.md)与[集成目录](../integrations/README.md)。

同一个 Agent 可以有多个进程或会话，核心的单一承接者约束只识别 ActorRef，不能据此保证只有一个进程工作。宿主需要把 ActivitySession 与 Assignment 的执行归属可信地绑定，并检查关联 Run 的操作资格；客户端自报 session 标识不能充当证明。恢复或接续要核对这项归属，不能让重复唤起的进程直接接管原会话。这里约束的是服务接受的操作，不能证明已失去资格的外部进程停止；具体方案与协议缺口记录在[设计发现](protocol-findings.md)。

## 委派后的可选唤起

委派创建可同事务提交 Task、项目关联、定向策略及可选 WakeRequest；之后也可以独立申请新的唤起意图。只有已提交的任务和请求允许触发外部启动。WakeRequest 记录目标、TaskRef、请求者和 LaunchProfile 的确定版本，由应用宿主异步处理。唤起失败、重复或结果未知均单独留痕，不取消已登记任务，也不把 Task 改成“已执行”。没有配置唤起时，目标仍可通过主动发现领取。

LaunchProfile 由管理者在受控宿主中配置，描述允许的启动程序、固定参数和有限的结构化输入。请求者只能选择有权使用的配置，任务目标、提示词、产物内容和任意字符串不能拼接为 shell 命令。配置变更不能静默改写历史请求所使用的版本；凭据注入、执行目录、资源限制和进程控制属于宿主职责。当前不提供任意任务脚本执行能力。

处理唤起前重新核对任务、目标资格、身份启停与配置授权；即使启动成功，也只有目标以真实身份成功 claim 后才取得任务责任。重复通知可以由领取守卫挡住，但这不保证外部进程只启动一次。启动响应未知时先保留未知结果并核对，不盲目重启制造多个进程；对外部启动副作用的对账与受控重试必须另有明确规则。

## 人与 Agent 如何共同验收

示例：人 H 发起父任务 P，Agent A 承接 P；A 发起子任务 C，Agent B 承接 C。B 提交 C 后，由 **A** 决定 C 是否完成。A 可以另外发起评审任务 R，让 H 提交评审意见；A 验收 R 的交付后，综合 C 与 R 的结果提交 P，最终由 **H** 验收 P。

每一次验收都对应自己的任务发起者。人的管理员身份不允许绕过这一规则；完成 R 不会给 H 增加 C 的决定权，也不会直接完成 P。评审产物中的“建议拒绝发布”与“评审任务交付被接受”可以同时成立，是否继续发布由应用明确的门禁政策判断。

若希望某个人直接验收一项工作，应由该人真实发起相应任务。当前草案的 issuer 不可变；不能通过改显示名、管理员操作或重建客户端来转移它。发起 Agent 暂时不可用时，任务保留待处理事实；恢复同一身份或未来的明确授权方案，需要另外处理，不能伪造决定。

## Agent 注册与定向领取

目录中身份的主键是稳定 ActorRef。显示名、模型说明、主机和凭据更新均不改变它；同名 Agent 不自动合并。Agent 登记说明“这个参与者是谁”，不自动授予所有任务的执行、读取或验收权限。

定向领取以任务为范围，只允许选定 Agent 发起 claim。它不是推送执行或替 Agent 自动领取；通知只是提醒。界面应区分“指定待领取”和“已经承接”。任务被指定给 A 后，B 即使知道任务 ID，也必须被拒绝新 claim；是否允许 B 读取任务由独立读取政策决定。

任务创建和初始定向策略必须原子生效，避免任务先公开、限制稍后写入的窗口。最小设计只允许发起方在 `offered` 时修改定向策略，并对策略版本和 claim 做一致性校验；修改策略不能抢走当前承接。需要转交时，先按协议释放，再修改策略并由下一位参与者主动领取。

停用 Agent 不删除身份或历史，也不自动取消任务、释放承接或确认外部执行已停止。宿主分别判断新命令准入与历史回执读取；允许读取旧结果不恢复执行权。停用后的恢复保留原身份，并重新校验现有承接及权限，不复活已经结束的 Assignment。

## 预期变化、汇总与交接的边界

发起者修订预期时保留旧版和原因，既有执行与提交仍指向原依据。接收方可以汇报对要求的疑问，但不能自行改写发起方预期；需要采用新依据执行时，遵循协议结束旧承接并重新开始。

项目摘要展示目标、当前任务、近期交付、未决问题和下一步，并标明来源、生成时间及所依据的版本。它是便于接续的入口，不能把未验收的交付描述为已完成，也不能让过期摘要覆盖更新的事实。写入 handoff 使用应用层版本检查，冲突时保留原记录并要求重读。

多个子任务完成不自动完成父任务。汇总者必须说明使用了哪些交付、遗漏了什么、仍有什么风险，再由汇总任务或父任务的真实发起者判断。一个子任务拒绝、失败、停用或接续，不隐式改变其他任务。

## 从实践反馈协议

日常使用要回答：现有操作是否表达了真实责任，参与者是否能接续工作，哪些步骤被迫依赖应用私有约定。设计阶段已经发现的问题记录在[协议设计发现](protocol-findings.md)，不冒充运行复现；实际使用发现缺口时保留最小场景与公开消息，不在 demo 内静默改变协议状态或角色。具体功能、故障和容量验证见[验证与压测计划](validation.md)。

本页描述的是目标行为。当前没有任务服务、身份注册接口、可运行 skill 适配、会话登记服务、唤起执行器、前端或真实 Agent 接入；没有执行任何启动命令，也没有产品可用性结论。
